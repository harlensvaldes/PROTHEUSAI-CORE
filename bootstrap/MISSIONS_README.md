# Missions

To create an explicitly opted-in v5 local fictional experimental mission, use `python scripts/new_mission.py --id DEMO-900 --title "Pilot" --risk HIGH --orchestrator orch --architect arch --profile LOCAL_FICTIONAL_EXPERIMENTAL --project-id pilot --owner-decision-ref "Owner decision reference"`. All Gates begin PENDING. Without the three scope arguments, creation remains v3. v5 is a new record, not a migration or conversion of historical decisions; existing missions require a separate adoption decision and preserved history.

The v5 review block has the v3 fields plus `scope_digest` and `reviewer_session`; see `docs/QUALITY_EVIDENCE_PROTOCOL.md` for the canonical digest. `validate` and `status` check structural consistency; `can-implement` reports whether Gate 1 records exact PASS and `can-close` reports whether all three and Owner acceptance are recorded. These diagnostics do not grant or deny Owner authorization or runner permissions. The profile excludes CRITICAL, real data, public exposure and operational use. The CLI cannot verify these real-world conditions or the authenticity of declarations. I0/G0 do not certify independence or identity.

Create a mission with python scripts/new_mission.py --id DEMO-900 --title "First mission" --risk MEDIUM --orchestrator orch-01 --architect arch-01. New schema v3 Gates start PENDING with review null; developer remains unassigned until actual work.

A review is a single protheusai-review JSON block in a report, with the manifest storing only decision and review {file, sha256_lf, reviewer_verification}. See QUALITY_EVIDENCE_PROTOCOL.md and quality/controls.json for evidence, risk matrix and limitations. The CLI validates consistency, not identity, isolation, truth or Quality certification. PWR is not PASS. `can-implement` reports review status; its exit code does not grant or deny the Owner's authorization or runner permissions.

v1 and v2 manifests with any non-PENDING Gate are historical: validate checks structure only and emits a warning, without extending their approvals; can-implement and can-close never enable them. v2 with every Gate PENDING can migrate mechanically to v3. If preserving a v2 manifest, record its raw SHA-256 and rename the unchanged bytes to mission.v2.json; then create a v3 manifest with new PENDING Gates. Do not infer identities or transfer prior approvals.

Derived projects must upgrade quality/controls.json to schema_version 2 with complete independence_minimums. Without a valid monotonic matrix the v3 CLI fails closed.

The optional v4 local-fictional HIGH Gate 1 waiver is described in `docs/QUALITY_POLICY.md` and `docs/QUALITY_EVIDENCE_PROTOCOL.md`. It does not import itself into derived projects, alter their Gates or certify identity. A separate Owner decision is required before any project adopts or uses it. Existing v1–v3 records keep their existing interpretation.

For a v4 exceptional record, keep `gate1` as `{"decision":"PENDING","review":null}`. Add `pilot_project` with exactly `id` and `local_fictional`, and `gate1_waiver` with exactly `id`, `mission`, `project_id`, `owner_id`, `authorization_ref`, `issued_at`, `not_before`, `expires_at`, `actions`, `exceptions`, `technical_review`, `artifact`, `revocations`, and `prior_failures`. Timestamps use `YYYY-MM-DDTHH:MM:SSZ`; `exceptions` is exactly `I1_CONTEXTO_SEPARADO` and `G1_EVIDENCIA_REGISTRADA`, while `actions` is a nonempty subset of `implement`, `gate2`, `gate3`, `close`. The technical report uses the existing review block, with decision PASS as a technical result only, the actual isolation declaration, and separate execution evidence. Artifact references are mission-relative SHA-256 LF references; prior FAIL entries have `path` and exact-byte `sha256_bytes`. A revocation entry has `at`, `reason`, `owner_ref`; any such entry blocks further action. The Owner must independently compare the authorization, scope, sessions, revocation and history with the channel under their control before acting. `can-implement` and `can-close` deliberately return nonzero even when the waiver is structurally eligible: a manual verification message is not autonomous authorization.
